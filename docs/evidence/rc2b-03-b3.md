## 3. Real process topology

```text
test host (unprivileged, inside the delegated cgroup subtree)
  ├── M1RecoveryScope (controller-side, per test)          [controller association]
  │     └── owner process  (dotnet Gagamba.Execution.Linux.M1.Owner.dll)
  │           ├── capability store + primary domain lease + journal writer
  │           ├── BubblewrapAdapter -> bwrap 0.11.1 (pinned) -> coordinator (fixture)
  │           │        └── fork/exec /tool  (the fixed fixture target, after RELEASE)
  │           └── ReleaseArbiter + HeldExecution (the sole RELEASE writer)
  └── (B2 composition tests) recovery executable (dotnet ...M1.Recovery.dll)
        └── B2 owner (lifeline or retained-domain barrier owner)
```

The release-capable association is the controller-created private inherited
SOCK_SEQPACKET channel (`OwnerProtocolChannel`): identity-bound, per-direction
sequenced, created by the controller, never passed through the recovery
process. The recovery process holds only the accepted B2 wire
(`Associate/Ready/Stop/Inspect/Snapshot/Reconnect/Refused`) and reports
`ReleaseAuthority = false`; no preparation or release message exists there.

### Topology conflict for release-through-recovery (explicit finding)

A separately authenticated **release-capable controller-to-owner** association
bundled into the current B2 topology is not implementable without granting the
recovery process release authority:

1. In B2 the controller's only authenticated association is with recovery
   (`RecoveryWire` + single-use session credential, which recovery itself
   authenticates), and the owner's only association is with recovery; the
   controller has no direct channel to the owner.
2. Routing release requests through recovery makes every request forgeable and
   replayable by recovery (it would hold a symmetric authority on the only
   path).
3. Delivering a direct controller→owner channel by passing the owner-end
   descriptor through recovery hands recovery a duplicateable bearer: any
   holder of that descriptor can read, inject or MITM the in-band handshake,
   and no kernel-enforced closure of the intermediate copy is attestable. This
   is exactly "passing a release bearer capability through recovery".

Per the commission, that dependent integration is **stopped** and reported
here. B3 binds release to the controller-owned authoritative association that
the owner transaction already uses, and demonstrates the separation: with the
B2 recovery process killed while the transaction owner is HELD, no recovery-side
fact changes and the authorized release still executes the fixture
(`B3RecoveryDeathWhileTheTransactionOwnerIsHeld...`). A future integration
requires either a controller-parented transaction owner with recovery retaining
only lifeline duties, or B6-grade pinned controller→owner authentication.

## 9. Failed initial attempts and corrections (preserved)

1. **Exec/root persistence refused (first positive-fixture run).** The owner
   persisted `ExecObservation` and `RootObservation` in one journal mutation;
   the accepted transition model admits exactly one release/stop/observation
   fact per transition, so the write was refused and the journal kept only the
   committed release. Corrected to two sequential acknowledged mutations.
2. **Disposal stop/abort interleave (class-ordered runs, ~50% flake).**
   Disposal submits a stop and then aborts; both exchanges ran concurrently on
   one sequenced channel. The abort received the stop's `StopDecision`, left
   the owner alive, and its journal flock then blocked reconciliation (cleanup
   Unknown). Corrected by a reentrant per-owner exchange gate in
   `M1RecoveryScope` and by settling the submitted stop (bounded) before the
   abort exchange in the B3 bridge. The class then passed 6/6 consecutive
   rounds and the full profile.

Both failures surfaced real ordering defects and were fixed in the
authoritative path, not masked; both raw runs remain preserved locally.

## 11. WSL2-only limitations and deferred gates

- WSL2 is a development/qualification environment, not a native Linux host;
  kernel, glibc, dotnet and toolchain identities are recorded above.
- The fixture topology requires the host to run inside the delegated cgroup
  subtree because the kernel `clone3(CLONE_INTO_CGROUP)` containment check
  requires write access to the common-ancestor `cgroup.procs`; the operator
  layout used is recorded (§10). No independent native Linux host exists yet.
- The fixture coordinator is a test-only build artifact; the fixture target,
  coordinator and policy are not installed/deployment-attested (B6).
- B4 protected capture and complete independent stop enforcement remain
  unimplemented: populated restricted-domain stopping is exercised only for
  the cooperative fixture (cgroup kill + events readback); hostile-population
  stopping, capture integrity and cleanup independence are not claimed.
- B5 sealed C3 durable deadline/reconciliation is not implemented; the test
  clock limitation is stated in §5.
- Hufu integration, public package publication, release tags, production
  provider activation and same-UID hostile-process isolation were not touched:
  `RestrictedExecutionRuntime.Create()` still returns the unavailable
  production provider, and the B3 composition is reachable only through the
  explicit internal pinned profile.
