## 2. Delegation and preflight

- cgroup2 mount: `/sys/fs/cgroup`, fs type `cgroup2`, mount ID `356`,
  options include `nsdelegate`. Read from `/proc/self/mountinfo`; never a
  supplied string.
- Boot ID: `/proc/sys/kernel/random/boot_id`
  (`5a6f8a5a-c5ab-4738-b337-d1cf4e29a770`).
- Root cgroup `cgroup.controllers` = `cpuset cpu io memory hugetlb pids rdma`;
  `cgroup.subtree_control` = `cpu memory hugetlb pids rdma`.
- Delegation, two distinct evidence classes:
  - **Root-native regression harness (not unprivileged evidence).** The
    root harness creates its own disposable parent under `/sys/fs/cgroup`
    and enables `+memory +pids` there. This proves the mechanism works when
    the caller happens to be privileged; it is **not** evidence of
    unprivileged pre-existing delegation and is never counted as such.
  - **Unprivileged delegated qualification (G2-10).** The operator
    supplies an already-existing delegated parent; the tested process runs
    as uid 1000 with no capabilities. Gagamba itself opens that parent and
    verifies prerequisites (`CgroupInterop.TryVerifyDelegatedParent`: on
    cgroup2, `memory` and `pids` present in both `cgroup.controllers` and
    `cgroup.subtree_control`); it never creates or repairs delegation.
    Missing/insufficient delegation refuses (`MissingDelegationRefuses`
    root-native; `MissingDelegationRefusesWithoutProvisioning` non-root).
- pidfd/subreaper: kernel 6.6; `PR_SET_CHILD_SUBREAPER` set and read back
  verified (`SubreaperEnabledAndVerified`, `NonRootDelegatedPreflightSucceeds`);
  a reparented orphan is proven adopted and reaped in both root-native and
  non-root delegated conditions (Section 10, Section 18).

## 3. Stable domain identity

`DomainIdentity{ ExecutionId, BootId, CgroupMountId, CgroupMountFsType,
ParentDevice, ParentInode, ChildName, ChildDevice, ChildInode,
LeaseGeneration }` plus the live handles held by the backend. Mount
identity comes from the real mount; parent/child resolution is
beneath-only, no-follow (`RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|
RESOLVE_NO_MAGICLINKS`). `Corroborates` compares every identity field
**including child device and inode** (G2-09 corrected this in R2;
`EveryIdentityFieldMismatchRefuses`, `DomainIdentityTests`); the mount
identity is derived from the retained descriptors via `statx(STATX_MNT_ID)`
+ `fstatfs` (`CGROUP2_SUPER_MAGIC`), not from the mountinfo string.
`SameNameButReplaced` detects a same-name different-inode swap.

## 4. Allocation ordering and pre-opened controls

Order: persist `AllocationIntent` → generate fresh child name → `mkdirat`
under the retained parent → open+stat the domain dir → capture identity →
open controls → verify each control's device matches the domain dir →
build identity. Pre-opened: domain directory, `cgroup.kill` (O_WRONLY),
`cgroup.events` (O_RDONLY), `memory.max`/`memory.swap.max`/`pids.max`
(O_RDWR). WP03 installs no limits (WP06). `EEXIST` on the child name
refuses; nothing existing is adopted.

## 5. Whole-domain stop and identity-checked removal

Stop writes `1` through the retained `cgroup.kill` handle and polls the
retained `cgroup.events` handle for `populated 0` with a bounded deadline
(25 ms interval). No PID enumeration, no journal PID kill, no pathname
re-open. Removal re-looks-up the child under the retained parent,
requires the exact captured dev/ino, then `unlinkat(AT_REMOVEDIR)`. A
same-name replacement refuses removal and reports Unknown.

## 6. Journal format and durability

Bounded little-endian snapshot, version 2 (R4 added creation identity and
cleanup progress), ≤64 KiB, ≤128 allocations,
sequence-monotonic, SHA-256 checksum over the payload. Fields: version,
sequence, execution id, boot id, cgroup mount id/fs, parent dev/ino,
domain name/dev/ino, lease generation, writer kind, cleanup state,
preparation stage, staging-parent dev/ino, a bounded allocation inventory
(kind, name, length, digest, device, inode, confirmed), a completed-cleanup
component bitmask, and optional recorded preparation identity. Excluded:
release credentials, release writer, secrets, raw input, unbounded logs.
Durability (G2-04 corrected in R3): two bounded generations
(`gen.a`/`gen.b` + transient `gen.tmp`); commit is resolve-baseline → free a
slot → exclusive-create/write/fsync `gen.tmp` → rename → fsync(dir)
[candidate] → unlink old slot → fsync(dir) [retirement]. A generation is
acknowledged only after retirement confirms; a failed final fsync keeps the
old acknowledged generation (Astra replacement case) and the reader never
promotes unconfirmed bytes. Writer authority (G2-05 corrected in R3) is a
mandatory `JournalWriterLease` created only after the storage lock is held;
every mutation requires the live lease, the sequence advances by exactly one
under the fence, and cross-process exclusion plus death-takeover are proven
(`LiveOwnerExcludesRecoveryWriter`, `DeadOwnerTakeoverContinuesSequence`).

## 7. Owner DomainLease ownership and bootstrap

Per plan Section 5 (line 128) and WP04 (`IHeldLauncher.PrepareHeldAsync(
PreparedTransaction, DomainLease, ...)`), the per-execution **owner** is
the primary `DomainLease` holder; the **recovery scope** holds separately
owned duplicates. WP03 implements exactly this:

- The scope opens the domain and retains a recovery duplicate.
- The scope transfers the primary descriptors (parent, domain dir,
  `cgroup.kill`, `cgroup.events`, `memory.max`, `memory.swap.max`,
  `pids.max`) to the owner over **one inherited Unix socketpair via
  SCM_RIGHTS** (`Native/FdPassing.cs`), then closes the socketpair and its
  own primary copies.
- The owner rebuilds the primary `DomainLease` from the received
  descriptors and can invoke whole-domain stop. The scope's independently
  owned duplicate can also stop/observe/remove.

Only the owner and recovery scope can invoke domain stop; the socketpair is
never filesystem-bound and carries no release authority. Bootstrap roles
(exact, once each, nothing else): ControlRead (fd 0), ControlWrite (fd 1),
RecoveryEvidence (fd 2), HandleChannel (inherited socketpair fd). No named
listener, service, reconnect API or serialized bearer token exists.

## 8. Writer transfer

The scope writes allocation/bootstrap snapshots under its lease; the owner
acquires the journal writer lease after receiving the primary handles
(observed as `WRITER_LOCKED`). One writer at a time: a live owner excludes a
rival writer (`LiveOwnerExcludesRecoveryWriter`, real owner process), and
after owner death is established via the retained pidfd/direct-child wait the
kernel-released lock is taken over with monotonic continuation
(`DeadOwnerTakeoverContinuesSequence`; the G2-05 review correctly noted the
older `NativeWriterLockIsExclusiveAcrossProcesses` used two objects in one
process, so it is retained only as a same-process check, not as cross-process
evidence).

## 9. WP02 integration (durability order)

`PreparationOwnershipCoordinator` is a portable ordering seam. The **real**
native integration is `M1RecoveryScope.AllocatePreparation` (G2-03 corrected
in R4): with the caller-held writer lease it writes `AllocationIntent`
(planned, unconfirmed names) → creates the domain and staging parent, captures
identities and retains recovery authority → writes `AllocationRegistered`
with actual identities → WP02 `SafeCopyIn.Prepare` with **incremental

`IntentFailurePreventsStaging` and the R4 barrier matrix
(`IntegratedBarrierTests`, `NonRootQualificationTests` G2-10 cases) prove the
order. No WP02 copy/binding code changed.

### G2-01 — explicit native FD ownership

Defect (reproduced by the reviewer): the scope's delegated-parent FD was
handed to the domain backend, which closed it; the scope then closed the
same number again, potentially closing an unrelated reused descriptor.

Correction: `CgroupInterop.TryCreateDomain` duplicates the parent FD and
the backend owns its own descriptor (`_parentFd`); the scope's
`_parentFd` is never transferred to or closed by the backend. Ownership
rules now: exactly one owning wrapper per descriptor unless an explicit
`Dup` (F_DUPFD_CLOEXEC) creates a second independently owned descriptor.
Transitions are either ownership transfer (sender invalidates its holder:
`backend.Dispose()` after SCM_RIGHTS send, `SpawnOwner` closes the child
socket end, `AllocateDomain` closes the parent socket end once) or an
explicit CLOEXEC duplication (recovery duplicate; backend parent dup).
Every failure path closes each endpoint exactly once. Deliberate
FD-number reuse is exercised by
`DomainAuthorityTests.ScopeDisposalDoesNotCloseReusedDescriptor` (open a
sentinel after allocation, dispose the scope, assert the sentinel is
still valid) and `RepeatedScopeDisposalIsSafe`.

FD ownership before/after transfer:

| Descriptor | Owner before transfer | After transfer |
|---|---|---|
| Delegated parent | scope retains; backend has its own dup | scope still owns its copy; owner has an SCM_RIGHTS dup |
| Domain dir, kill, events, memory.max, memory.swap.max, pids.max | backend (owns) | owner (owns SCM_RIGHTS dups); scope keeps recovery dups; backend copies closed once |
| Recovery duplicate set | scope (owns F_DUPFD_CLOEXEC dups) | scope (unchanged) |
| Socketpair parent end | scope (CLOEXEC) | closed by scope after send |
| Socketpair child end | scope (inheritable) | owner receives, then closes it |

### G2-02 — strict SCM_RIGHTS wire contract

`Native/DomainHandleTransfer.cs` defines one bounded versioned message:
magic `0x4D314654`, version 1, flags 0, execution UUID, lease-generation
UUID, role count and the exact ordered role list
(`Parent, DomainDirectory, Kill, Events, MemoryMax, MemorySwapMax,
PidsMax`). The message is validation evidence; the passed FDs remain the
authority; no release authority is representable. `FdPassing` receive uses
`MSG_CMSG_CLOEXEC`, inspects `msg_flags` (rejects `MSG_CTRUNC`/`MSG_TRUNC`),
validates the exact payload length and control layout, rejects extra
ancillary/unknown SCM levels, requires the exact descriptor count, verifies
every received descriptor has `FD_CLOEXEC`, and closes every received
descriptor on any rejection path. The bootstrap socket is bootstrap-only
and is closed by the owner immediately after reception (and on every
failure path).

Malformed-transfer native matrix (all refused; received FDs closed):
too few descriptors; too many descriptors; truncated payload; missing
CLOEXEC; parent-as-child alias; swapped kill/events (access mode);
sibling `cgroup.events`; `/dev/null` as a role. Portable message matrix
(`DomainHandleTransferTests`): bad magic, wrong version, nonzero flags,
wrong execution, wrong lease, truncated payload, nonzero reserved,
role-order mismatch, duplicate role. `ExecProbeProvesReceivedDescriptorsDoNotSurvive`
spawns `/bin/sh` and confirms a non-CLOEXEC control fd is inherited while
a received authority fd is not.

### G2-04 — bounded two-generation durability

- Rejected behavior (reproduced by the reviewer): rename(candidate →
  current) destroyed the old acknowledged snapshot, then a failed final
  directory fsync left the reader seeing the unacknowledged replacement.
- Correction: the journal keeps two bounded generation slots (`gen.a`,
  `gen.b`, each ≤64 KiB) plus a transient `gen.tmp`; no unbounded
  history. Commit order: resolve baseline → free a slot (unlink
  higher-sequence debris) → exclusive-create/write/fsync `gen.tmp` →
  rename to the free slot → fsync(dir) [candidate established] → unlink
  the old slot → fsync(dir) [retirement]. Success is reported only after
  retirement confirms; any earlier failure leaves the old acknowledged
  generation intact.
- Acknowledgement point: a generation is acknowledged only by a fully
  completed write. Reader rules (conservative, never invent durability):
  no slot → none; one valid slot → acknowledged; both valid → the lower
  sequence; anything else → explicit uncertainty/refusal. In-memory and
  durable sequence advance only on success; a failed write never advances
  them even when the new bytes happen to be established.
- Bounded reads: native storage inspects `FileInfo.Length` before
  allocating/reading and refuses overlong files; the journal re-checks
  decoded length against the 64 KiB bound.

### G2-05 — fenced writer lease and monotonic sequence

- Rejected behavior (reproduced by the reviewer): a process that failed
  the flock could still call `OwnershipJournal.Write` successfully, and a
  fresh writer reset durable sequence 2 to 1.
- Correction: `JournalWriterLease` is created only by
  `OwnershipJournal.TryAcquireWriter` after the storage lock is held; it
  cannot be forged from a PID, path or sequence. Every mutation
  (`Write`, `WriteNext`, and therefore allocation-intent/registration/
  owner-acceptance/Prepared records) structurally requires a live lease
  bound to that journal; released/foreign/missing leases refuse. The
  lease seeds its baseline from the last acknowledged durable snapshot
  under the fence; `WriteNext` advances by exactly one with checked
  arithmetic; explicit `Write` must equal baseline+1 (regression,
  duplicates and gaps refuse).
- Scope→owner transfer: the scope writes allocation/bootstrap records,
  releases its lease, and spawns the owner; the owner validates bootstrap
  and acquires its own lease (observed `WRITER_LOCKED`). Two independently
  usable leases never exist; the transfer uses no release authority and
  does not weaken the SCM_RIGHTS domain-handle contract.
- Live-owner exclusion: while the owner holds the real lock, a second
  writer fails acquisition and cannot reach any mutation API; disk
  bytes/sequence are unchanged (`LiveOwnerExcludesRecoveryWriter`).
- Death takeover: after owner death is established via direct-child wait,
  recovery acquires the kernel-released lock, loads acknowledged N, and
  writes N+1 (`DeadOwnerTakeoverContinuesSequence`).
- Lock lifetime: `flock` on an open lock file, released by the kernel on
  process death; `JournalWriterLease.Dispose` relinquishes exactly once;
  no hidden duplicate keeps the lock alive (verified by the death and
  exclusivity tests).

### 19.1 Defect and independent counterexample

The bootstrap transfer used `SOCK_STREAM`. A stream endpoint does not
preserve the intended 51-byte logical message boundary. The receiver
supplied a 51-byte buffer, so a sender that transmitted a valid 51-byte
payload plus one extra byte produced exactly this independent result:

```text
REAL_DOMAIN_OVERLONG: sentBytes=52 receivedBytes=51
received=True decode=True domainValid=True
```

`recvmsg` returned the valid 51-byte prefix, no `MSG_TRUNC` was required,
the extra byte stayed queued, and the metadata decoder accepted an
apparently exact 51-byte message. The owner then closed the endpoint,
discarding the evidence.

### 19.2 Corrected framing mechanism

`Native/FdPassing.cs` now creates the inherited bootstrap endpoint with
`SOCK_SEQPACKET` (`AF_UNIX`). One `sendmsg` is exactly one `recvmsg`
record, so the kernel preserves the logical message boundary. The receiver
still allocates exactly the expected 51-byte payload buffer and performs
its exact-length, `MSG_TRUNC`, `MSG_CTRUNC`, control-count/layout and
`FD_CLOEXEC` checks. On a message-preserving endpoint an overlong record is
reported with `MSG_TRUNC` instead of being silently split. After a
successful single receive, the receiver additionally requires that no
second record is queued, using `ioctl(FIONREAD)` (which reports the next
record's length without installing its descriptors; `MSG_PEEK` was rejected
because it duplicates SCM_RIGHTS descriptors on this kernel). Socket
creation fails closed: if a message-preserving socketpair cannot be created
the transfer refuses and never falls back to the vulnerable stream
behavior. The extra-frame check, the `MSG_TRUNC`/`MSG_CTRUNC` paths and
every other rejection path close all received descriptors.

Exact message-boundary guarantee: the accepted metadata is the whole
logical message and its length is exactly
`DomainHandleTransfer.ExactPayloadBytes` (51). A longer record refuses
(`MSG_TRUNC`); a shorter record refuses (length mismatch); a second record
refuses (pending-frame check); truncated or extra ancillary data refuses
(`MSG_CTRUNC` and control-count/layout checks).

## 20. G2 remediation R6C (G2-04 acknowledged durability, G2-05 writer fencing)

Basis: the preserved independent G2 rereview left G2-04 and G2-05 blocking
with exact counterexamples (quoted below). These findings are paired:
G2-04 defines which generation is durably acknowledged, G2-05 defines
which writer may advance it. Implementation-under-test:
`cbe8739` (this tranche changes only the journal durability protocol, the
writer-fence ownership model, and their tests; G2-03/G2-08/G2-10 are

### 20.1 G2-04 original defect and required invariant

The rereview reproduced, with acknowledged durable sequence 1 present and a
candidate sequence 2 fully staged:

```text
FSYNC_FAIL_2: write=False last=1 baseline=1 reopened=2 reopenedInode=777
GENESIS_FAIL: write=False last=0 reopened=1
```

Retiring the old generation before the final directory sync was confirmed
promoted the failed candidate to acknowledged state on reopen, and the
two-slot "lone slot is acknowledged" rule could not distinguish a committed
generation from an unconfirmed candidate. Required invariant: if a journal
mutation returns failure, a fresh reader must yield the last previously
acknowledged generation or explicit conservative uncertainty — never the
failed candidate. A successful return may occur only after all durable
metadata transitions needed by recovery are complete.

### 20.2 New acknowledgement protocol

`Recovery/OwnershipJournal.cs` implements a deletion-sealed commit over a
bounded layout (`gen.a`, `gen.b`, `gen.tmp`, `gen.seal`, `ownership.lock`;
all content ≤64 KiB; no history growth). A sealed commit performs, in
order: best-effort `gen.tmp` scratch cleanup (ignored); exclusive-create
`gen.seal` + file/directory sync (ambiguity explicitly opens); stage the
candidate into `gen.b` (complete write, file sync, atomic rename,
directory sync); mirror it into `gen.a` the same way; unlink `gen.seal`.
Old generations are never unlinked — each slot is overwritten by an atomic
rename — so no retirement step can orphan acknowledged state.

Acknowledgement is a content property (both slots holding the generation,
every rename preceded by a complete fsynced write and followed by a
directory sync). The seal never acknowledges; its presence only overrides
content reading with explicit uncertainty while a commit is in flight.
Removing the seal therefore needs no durability confirmation of its own: a
torn removal leaves a stale, recoverable override, never a false
acknowledgement. The acknowledgement point is the completed mirror phase;
success is reported only after the seal removal syscall succeeds.

Reader rules: seal present → explicit uncertainty (never promotion);
no slots → nothing acknowledged; one valid slot → acknowledged; both
valid and equal → acknowledged (the normal steady state); both valid and
unequal → the lower sequence (acknowledgement requires both-equal, so the
higher is necessarily uncommitted); anything else → uncertainty/refusal.

Failure rollback: on any pre-acknowledgement failure the seal is removed
best-effort exactly when the acknowledged baseline still decodes from a
slot (restoring readable old state); otherwise — genesis, unreadable
slots, or a complete newer generation only the seal deletion could confirm
— the seal stays and the reader reports uncertainty. Crash between failure
and rollback likewise leaves uncertainty. A crash after reported success
but before the seal removal persists also surfaces as uncertainty over
complete content, which explicit recovery completes.

Explicit recovery (`TryRecoverCommit`, takes the fence and refuses while a
live writer holds it): both slots decodable → removes only the seal,
returning the acknowledged generation (both-equal: the staged commit was
complete; unequal: the lower, demoting the uncommitted higher); no slots →
removes the seal, returning nothing; lone or uninterpretable sealed state
→ refuses with the seal left for operator resolution. Recovery never
deletes generation content and never chooses the highest visible sequence.
Neither acquisition nor mutation auto-resolves ambiguity.

### 20.4 G2-05 original defect and corrected model

The rereview reproduced against the real storage (the portable fake

```text

RIVAL_LOCK=True ... survivingLeaseWrite=True
```

## 22. R6D.2 — owner-owned preparation transaction

Implementation-under-test: `b3cbc979b022452dc528b8fbd84c7d1ad4470390` (source/tests commit).

### 22.1 Topology and architecture alignment

The prior implementation had M1RecoveryScope.AllocatePreparation perform
the complete transaction in the recovery-scope process: durable intent,
domain creation, SafeCopyIn, accounting, Prepared, and Mint. The
separate owner executable was domain-only. Killing that owner could not
represent interruption of production allocation/staging, so its death
coverage could not establish the plan's issuer/losable-actor failure model.

The R6D.2 topology is now:

- **Recovery scope:** external lifetime authority; direct-child subreaper;
  owner pidfd holder and reaper; delegated-parent and staging-parent holder;
  initial AllocationIntent writer; recipient of independently owned domain
  recovery handles and the exact staging-directory handle; reconciler; and
  recovery writer only after pidfd proves owner exit and the direct child is
  reaped. It receives only bounded descriptions and acknowledgements.
- **Owner:** issuer and actual transaction process; exact-intent verifier;
  sole live transaction-journal writer; scoped domain allocator and primary
  DomainLease holder; SafeCopyIn caller; incremental staging accountant;
  Prepared writer; and sole creator/holder of the issuer-local
  PreparationStore and minted capability. No target is released in this
  tranche.

Startup is ordered: scope durably writes AllocationIntent while holding
its real writer fence, then disposes that writer before spawning the owner.
The scope immediately retains the direct child's CLOEXEC pidfd before it
sends Start. The owner independently opens the journal and must acquire
the real exclusive writer fence and prove the matching acknowledged intent
for this execution, lease generation, boot identity, and journal. Its
ScopedAllocationContext is bound to that proof and to the effective live
writer; it refuses a foreign journal, stale/non-effective writer, mismatched
identity, or non-AllocationIntent latest acknowledged state. There are no
overlapping usable leases. After proven owner exit/reap, the scope may
acquire the same real fence and continue from the last acknowledged sequence.

This aligns with ADR 0003's external recovery owner-loss requirement and the
implementation plan's issuer-bound, owner-local preparation capability,
separate surviving recovery scope, retained handles, and no-resurrection
rule. The implementation plan's Section 10.1 sentence assigning domain
creation to the scope is clarified in the documentation commit: the scope
retains the delegated parent/envelope; the owner creates the domain and
transfers independent recovery authority before registration. This is the
previously approved G2-03 topology decision, not an ADR 0003 revision. The
future WP04 descriptor map remains separate: no domain, staging, journal,
recovery, release-writer, or output-reader descriptor is sent to a future
coordinator; no WP04 code or release protocol is added here.

### 22.2 Authority transfer and transaction path

M1RecoveryScope.StartOwnerPreparation replaces the scope-local
AllocatePreparation result contract with a bounded owner-preparation
operation returning only completion/barrier status and an
OwnerPreparedDescription. The old scope allocation helpers and old
owner domain-only command path are removed; CgroupInterop.TryCreateDomain
has one production caller, OwnerPreparationTransaction.

The scope passes only a versioned request and duplicated delegated-parent
and staging-parent descriptors in the inherited private
SOCK_SEQPACKET channel. The owner creates the real domain using its
ScopedAllocationContext. Before registration or further transaction
progress, the owner sends the exact recovery handle set with domain/mount,
parent/child device-inode and control identity; the scope validates and
retains independent descriptors, then acknowledges. The owner keeps its
primary lease. Neither side reconstructs recovery authority from a path,
PID, or journal record.

The owner invokes the existing SafeCopyIn and PreparationPublisher
path. Immediately after staging-directory creation, it sends the exact
created-directory descriptor and device/inode identity. The scope validates
and retains that handle before acknowledging retention. The owner then
writes the confirmed directory identity durably; the scope verifies the
journal state and sends StagingMayProceed. Only then may object copying
begin. Each successfully bound object is durably accounted by the owner
before it advances. The existing independent-byte, source/destination
identity, digest, bound, sparse refusal, no-follow/openat2, and
replacement-safe cleanup behavior remains in the reused copy engine.

After caller-provided manifest authorization is bound to the exact
execution, issuer, generation and canonical digest, the owner alone writes
Prepared, the scope checks that exact description against durable state
and acknowledges, then the owner creates its local PreparationStore and
calls the existing publication/Mint path. The scope has no store reference,
capability lookup route, serialized capability, release writer or recovery
Mint route. If the owner dies after durable Prepared and before Mint, no
store entry or capability exists to resurrect.

### 22.3 Private protocol and owner-side barriers

The inherited protocol is version 1 (M1OP), identity-bound to execution
and lease generation, sequence-checked per direction, message-preserving,
CLOEXEC for received descriptors, and bounded to a 60 KiB payload. It has
no filesystem address, reconnect, bearer serialization, or capability
message. Its transaction states are Start, WriterReady, StartAuthority,
DomainRecoveryAuthority / DomainAuthorityRetained, DomainRegistered /
DomainRegistrationRetained, StagingAuthority /
StagingAuthorityRetained, StagingAccounted / StagingMayProceed,
StagedObjects, ManifestAuthorization, PreparedDescription /
PreparedAcknowledgement, and Completed / Aborted. Test-only
BarrierReached / Continue transitions are ordered on the same channel.
The start transfer has exactly two descriptor roles (delegated domain parent,
staging parent); domain recovery uses the exact validated transfer count;
staging recovery uses exactly one created-directory descriptor. Unknown,
duplicate, stale, wrong-identity, wrong-type, over-bound or wrong-descriptor
transitions refuse.

The real owner transaction has deterministic barriers at:

1. `after-intent`;
2. `after-domain-retained`;
3. `after-registered`;
4. `after-staging-accounted`;
5. mid-staging (after one object is confirmed and before the next);
6. `after-copy`;
7. `after-prepared-before-mint`.

Native tests start and kill the separate owner while the scope remains live,
then exercise pidfd exit proof, takeover sequence continuity and retained
recovery cleanup. Tests also cover scope-writer exclusion while the owner is
alive, the missing staging-retention acknowledgement (no object copy),
capability absence from the scope outcome, and pidfd FD-number reuse on
scope disposal. These are topology/process tests and later qualification
barriers; they are **not** an accepted D1–D6 result.
