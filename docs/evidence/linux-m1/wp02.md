## 2. Source-root/staging-parent descriptor model

Two distinct trusted directory authorities, each opened once from the
harness-supplied bootstrap path (`O_RDONLY|O_DIRECTORY|O_NOFOLLOW|
O_CLOEXEC`) and verified with fstat to be a directory:

- source-root dirfd: all source resolution is `openat2` relative to it
  (`O_RDONLY|O_NOFOLLOW|O_CLOEXEC`,
  `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS`).
- staging-parent dirfd: per-preparation subdirectory created with
  `mkdirat` (mode 0700, must be fresh — `EEXIST` refuses); all staging
  creates/reopens/unlinks are relative to the retained subdirectory
  descriptor.

After bootstrap no pathname re-resolution and no pathname-based authority
exists on the object path: source opens, staging creates, reopens and
unlinks all take retained descriptors plus single-component names. The
two authorities are never conflated (separate handles, separate
lifetimes; roots/parents close when preparation completes, the staging
subdirectory handle transfers into the closure).

Holding a source FD pins the inode, never immutable content: drift
between pre-copy stat, streamed bytes and post-copy stat refuses with
`ObjectReplaced`.

## 3. Exact copy/binding/publication sequence

Per object, in order: name/role validation → `openat2` source open →
fstat (regular file, dense block accounting, initial budget screen) →
exclusive staging create (`O_CREAT|O_EXCL|O_WRONLY|O_CLOEXEC`, 0600) →
capture created identity → bounded descriptor-to-descriptor copy
(64 KiB buffer, per-object and total budgets enforced on streamed bytes
before each write, cancellation checked per chunk, streaming SHA-256) →
source re-stat (size must equal pre-copy size and streamed count) →
staged density re-verification → claimed-digest check → `fchmod` final
mode (tool 0500, input 0400) → file `fsync` → close writable FD →
read-only reopen under the staging dirfd with the same safe policy →
verify `(dev, ino)` equal, regular type, expected mode bits, expected
size, `nlink == 1`, dense accounting → rehash from the reopened FD and
require equality with the copy digest → bind.

Then: staging-directory `fsync` → closure (accounted) → manifest binding
check (staged roles/digests/lengths exactly match the manifest closure)
→ durable acknowledgement delegate → cancellation recheck → `Mint`.
`Mint` remains the atomic capability-publication boundary; no usable
capability exists before acknowledgement, and no early publication is
possible.

## 4. Budgets and identity fields

Section 7 values used by tests: tool ≤ 4 MiB (4194304), input ≤ 256 KiB
(262144), total staged ≤ 16 MiB (16777216), ≤ 128 objects,
argv/environment/config snapshot ≤ 16 KiB (16384). Exact-limit copies
succeed; limit+1 refuses before the first excess write.

Object identity fields: role, SHA-256, length, device, inode, mode,
staging name, retained read-only handle. Staging names are
deterministic (`{role}-{index:D3}.staged`).

## 5. Descriptor ownership at publication

Every opened descriptor has exactly one owner; errno is captured before
any cleanup. At successful publication no writable FD to any staged
object remains (portable: fake access-mode audit; native: `/proc/self/fd`
+ `fdinfo` scan asserting no `O_WRONLY`/`O_RDWR` on staged identities —
fdinfo is qualification evidence only, never semantic authority).
Retained object FDs are read-only; the staging subdirectory handle is
retained for explicit descriptor-relative cleanup; roots/parents close
at preparation end.

Framework-file-stream lesson recorded: `FileStream` over a
`SafeFileHandle` takes ownership and closes the descriptor on dispose,
which invalidated retained descriptors mid-preparation (observed as
`EBADF` on post-copy stat during native testing). Production therefore
copies through `UnownedFdStream` (raw read/write syscalls, disposal is
a no-op on the descriptor).

## 6. Cleanup: partial versus accounted

- Partial (never bound): owned FDs closed, staging file unlinked through
  the retained staging directory, no capability, no retained record.
  Pre-existing files are never deleted (collision test proves the
  planted file survives).
- Accounted (bound): on acknowledgement refusal, Mint failure, or
  cancellation after binding, objects stay in a retained closure for
  explicit `DiscardAccounted` cleanup/reconciliation; no usable
  capability is published.

## 7. Durability behavior

Per-object file `fsync` before close; staging-directory `fsync` after
all binds; caller-supplied durable-acknowledgement delegate before
`Mint`. No temporary-name/rename dance (exclusive create needs none;
`renameat` deliberately not wrapped) and no WP03 journal/recovery
system. If a future durability requirement needs recovery ownership,
that is a stop-and-report boundary, not silent scope growth.

## 8. openat2 qualification

Method: runtime probe issuing `openat2` with an invalid resolve bit —
`EINVAL` proves a supporting kernel, `ENOSYS` means Unsupported; never
inferred from kernel/glibc/architecture strings. This host: supported
via the libc symbol (`openat2@@GLIBC_2.43`). The raw-syscall path
(pinned `SYS_openat2` 437 on x64 and arm64; all other architectures fail
closed) is exercised directly by a native test and agrees with the
symbol path. Every real call still handles `ENOSYS` fail-closed with no
weakened fallback.

Sparse-file judgment call (corrected — the previous
"accepted by streamed-bytes rationale" is superseded and no longer the
disposition): sparse sources are refused per the explicit Section 7
requirement, independent of streamed-byte budget enforcement.
Mechanism: `st_blocks` counts 512-byte units, so fewer allocated bytes
than the logical size proves sparseness; absent block accounting
(`st_blocks == 0`) for a non-empty file cannot prove density and fails
closed. Checked at source admission, staged post-copy verification, and
reopen verification (`CopyFailureKind.SparseRefused`). Empty files are
trivially dense. Supported-filesystem assumption: sources and staging
must live on filesystems with reliable block accounting (ext4/tmpfs/
overlay qualified here; this host's 9p share synthesizes block counts
and is not relied upon). Streamed-byte accounting remains authoritative
for budgets; density is the separate admission check.

## 13. Limitations and nonclaims

- Staging parents are harness-owned temp directories in this WP02 slice;
  production delegation/ownership is WP03 and is out of scope here (see
  [wp03.md](wp03.md)).
- Acknowledgement is a caller delegate (fake in tests); durable journal
  semantics arrive with later packages.
- Empty staging directories from refused preparations remain for the
  harness to remove with the parent (never adopted or reused).
- Sparse/unreliable-block-accounting sources refused (`SparseRefused`);
  supported filesystems need reliable accounting (Section 8).
- Binding-time read-only reopen interpretation: the single reopen occurs
  strictly before binding, relative to the retained private staging
  dirfd, with full identity and digest re-verification. After binding no
  pathname reopen or reacquisition mechanism exists anywhere in WP02
  (verified by source audit: opens happen only pre-binding; the
  publisher performs no host calls; `DiscardAccounted` only unlinks).
  `RetainedDescriptorSurvivesPathnameRemoval` proves post-unlink
  authority stays with the retained read-only FD. No descriptor-topology
  change was required.
- TOCTOU limits: pre/post size equality detects observed drift; a
  truncation that stabilizes entirely between observations reads as a
  consistent snapshot (documented, inherent).
- Raw-syscall fallback tested directly on x64; arm64 layout compiled
  but not executed on this host.
- Fixture modes exist for later packages; constructor/useful-work/fail
  behaviors are unexecuted and unclaimed.
- WP02 proves none of: cgroup/domain ownership, owner-loss recovery,
  release/stop linearization, held coordinator semantics, target
  non-init-before-release, target execution, output enforcement, full
  no-IP, runtime closure sufficiency, .NET runtime support, P05/P06
  production qualification, production readiness.

## 15. G2 remediation R1 (G2-06, G2-07; commit recorded below)

Basis: independent G2 review `docs/reviews/gagamba-linux-m1-g2-review.md`

and G2-07). Only these two WP02 findings were corrected; no WP03 finding

### G2-06 — capability owns the exact bound closure

- Defect (reproduced by the reviewer): publication minted from
  manifest/identity/expiry while the `PreparedClosure` remained a
  separate lifetime, so
  `publish → DiscardAccounted → TryLookup/TryConsume` still succeeded
  with closed object handles; the selected
  `PrepareHeldAsync(PreparedTransaction, DomainLease, ...)` boundary
  therefore could not obtain the exact copied FDs.
- Correction: `PreparationStore.Mint` now takes the exact
  `PreparedClosure` and the store entry owns it for the capability's
  lifetime. `PreparedClosure.TransferToStore()` marks ownership; a stale
  builder reference disposing afterwards is a no-op (so builder/local
  scope disposal cannot invalidate store-owned handles), and only the
  store's `ReleaseFromStore()` (on invalidation/abort) closes handles —
  exactly once. `PublicationResult.Closure` is null on success (ownership
  transferred) and non-null only on failure for accounted cleanup, so
  there are no two independently disposing owners. Controlled borrow:
  `PreparedTransaction.TryBorrowClosure(out PreparedClosure?)` returns
  the store-owned closure for a live, non-aborted, reference-equal
  capability only; it never reconstructs from paths/names/identities and
  never transfers ownership. Reference-owned lookup/consume/foreign/
  expiry semantics are unchanged (G1 tests still pass).
- Negative case after correction: the published result exposes no
  disposable closure; discarding through the stale builder reference is
  refused (debt), and the capability keeps live handles. No state remains
  where a valid capability survives destruction of its authoritative
  closure.

### G2-07 — identity-checked staging cleanup

- Defect (reproduced by the reviewer): `DiscardAccounted` unlinked each
  recorded name under the retained directory without comparing the
  current entry to the retained object identity, ignored unlink results,
  then disposed authority; `FinishFailed` likewise ignored partial
  cleanup failures. A replacement occupying the same name was deleted.
- Correction: `StagingCleanup` (new, internal) resolves each entry only
  relative to the retained trusted staging-directory descriptor with
  no-follow semantics, compares the current entry's `(device, inode)` to
  the captured creation identity, and returns a truthful outcome:
  `Removed`, `AlreadyAbsent` (idempotent), `IdentityMismatch` (replacement
  preserved), `InspectionFailed`, `RemovalFailed`. `PreparedClosure.
  DiscardAccounted` and `SafeCopyIn` partial cleanup use it and retain
  handle authority / cleanup debt on any non-confirmed outcome instead of
  dropping it. `PreparationResult` gained a `Cleanup` report; a
  non-confirmed report retains debt. No recursive traversal, no
  pathname-only authority, no silent success.
- WP03 boundary: the WP03 reconciler's own cleanup remains a WP03
  blocker (G2-08); this tranche only adds the safe WP02 primitive WP03
  must later adopt. WP03 production behavior was not modified.

## 16. G2 remediation R6A (G2-06 rereview; `e5f90ce4c3c6a239775b4af72e26e077b292e6d5`)

Basis: preserved independent G2 rereview of `121c644`
(`docs/reviews/gagamba-linux-m1-g2-rereview.md`), which reproduced a
shared-closure counterexample against the R1 ownership model. Only G2-06
is corrected here; no WP03 behavior changes (no WP03 file touched), no
WP04 work, no G1 semantic change.

### Rereview defect

`TransferToStore()` set a Boolean without refusing an already-owned or
disposed closure, and `Mint` never checked exclusive closure ownership.
Two distinct capabilities could publish the same exact closure; invalidating
the first closed the shared authority while the second stayed usable:

```text
STALE_BUILDER: published=True handleClosed=False
SHARED_CLOSURE: secondPublished=True handleClosed=True lookup=True borrow=True consume=True
```

### Corrected ownership state machine

`PreparedClosure` now carries `ClosureOwnership` (`BuilderOwned` →
`StoreOwned` → `Released`, terminal), enforced by the closure object
itself under its own lock — never by caller convention:

- `TryTransferToStore()` performs the single builder-owned → store-owned
  transition atomically and refuses already-owned/released closures;
  concurrent claims yield exactly one success.
- Builder `Dispose()`/`DiscardAccounted` act only while builder-owned;
  stale builder disposal after transfer stays a no-op.
- `ReleaseFromStore()` (store-side invalidation/abort) closes handles
  exactly once via the atomic Released transition; sharing cannot exist,
  so one entry's release can never destroy another entry's authority.
- `AuthorityLive` reports live handle authority; the store re-checks it
  on borrow (defense in depth).

`PreparationStore.Mint` is atomic: all validation (issuer, generation,
digest, expiry, preparation-ID uniqueness) precedes the irreversible
transfer, so a refusal is side-effect free — the closure is untouched and
any existing owner is unaffected. Transfer, entry creation and dictionary
insertion run under the store lock (lock order always store → closure, so
no deadlock); the post-transfer steps cannot fail, so no rollback path
exists and ownership cannot strand. A claimed/released closure makes Mint
throw `ArgumentException` (surfaced by the publisher as a failed
publication returning the closure for accounted cleanup).

### Counterexample before/after

`ClosureOwnershipTests.RereviewSharedClosureSecondPublicationRefuses`
repeats the rereview steps against a real 128-byte copied closure:
publish A, stale builder dispose (handles stay open), publish the same
exact closure as B with an otherwise valid distinct identity, invalidate A.
After the correction `secondPublished=False`, no B capability exists, A
keeps working (lookup/borrow/consume on live handles), and invalidating A
closes the handles exactly once. The old
`secondPublished=True … consume=True` state is impossible.

### Further coverage

- Second Mint with the same identity refuses (preparation-ID uniqueness)
  and with a distinct identity refuses (claimed closure, no entry created);
  the first capability is unaffected in both cases.
- A digest-mismatched Mint refuses before the transfer; the closure stays
  builder-owned and a later valid Mint succeeds (no ownership damage).
- A builder-released closure cannot Mint.
- `ConcurrentMintOfSameClosureYieldsExactlyOneSuccess`: 32 concurrent
  Mints of one closure yield exactly 1 success and 31 refusals; the winner
  is fully usable.
- A twin capability with identical identifiers from another store is
  foreign and borrows nothing here, and vice versa. Duplicate consume
  remains impossible (`DuplicateConsumeDoesNotDuplicateOwnership`).
