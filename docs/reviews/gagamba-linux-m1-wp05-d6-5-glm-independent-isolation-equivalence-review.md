## 7. R2 property-propagation analysis

- **Edge-removal mechanism is real and correctly enumerated.** The design removes the six variant-only properties (`AssemblyName`, `DefineConstants`, `BaseIntermediateOutputPath`, `MSBuildProjectExtensionsPath`, `BaseOutputPath`, `IsPackable`) at the M1→`Gagamba.Execution` reference edge. This is implementable exactly as described: `Microsoft.Common.CurrentVersion.targets` (SDK 10.0.401, lines 1044/1073/1102) passes `RemoveProperties="%(_MSBuildProjectReferenceExistent.GlobalPropertiesToRemove)$(_GlobalPropertiesToRemoveFromProjectReferences)"` to the MSBuild task for each project reference, so `GlobalPropertiesToRemove`/`RemoveProperties` metadata on the `ProjectReference` item removes those global properties from the child build. The default list already removes `OutputPath` (lines 817-819, `PassOutputPathToReferencedProjects=false`); `BaseOutputPath` is not in the default list, so the design's explicit inclusion is necessary and correct.
- **Propagation consequences verified.** With the six removed, `Gagamba.Execution` evaluates its normal identity and paths; the test project's own reference to the core is clean because the variant properties live only on the M1 reference; Owner references the regular M1 project by explicit path with no variant properties; ambient globals (e.g., `Configuration`) flow identically in production and variant chains. No unexpected reference-assembly path, artifact collision, or identity inconsistency was identified for the enumerated property set.
- **The DefineConstants edge case.** Removing `DefineConstants` at the edge is necessary but not sufficient: the parent (variant M1) must first hold the correct constant set, and the design does not specify how the symbol reaches it. Independent evaluation demonstrated the natural route fails: passing `-p:DefineConstants=GAGAMBA_WP05_D6_4_TEST_FIXTURE` (the ProjectReference `Properties` equivalent) yields evaluated `DefineConstants` = the symbol **alone** — the SDK's `TRACE;RELEASE` is lost because project assignments cannot override a global property. Per the SDK source (`Microsoft.NET.Sdk.BeforeCommon.targets`, `AddImplicitDefineConstants` target, lines 290-298), the implicit framework constants (e.g., `NET10_0_OR_GREATER`) are appended by a target-execution-time assignment, which a global property likewise suppresses — so the naive route would also drop the implicit framework defines, a far larger divergence than the symbol-only delta the design requires. Additionally, MSBuild splits `Properties` metadata and `-p:` switch values on `;` (demonstrated: `MSB1006 "Property is not valid. Switch: RELEASE"`), so delivering a multi-constant union requires `%3B` escaping. See section 12 for the required amendment.

## 8. R2 source-graph comparison assessment — sufficient

The documented future verifier (D6.5 §5; amended D6.4 §4 "Source-graph and conditional-compilation verification") satisfies the required properties:

1. Actual compiler inputs are collected from both builds — evaluated `Compile` items **and** the actual Csc source list from a build binlog after generated inputs are added (§5.2).
2. Tracked sources are normalized to canonical Git-root-relative paths (§5.3).
3. Bidirectional set equality `P=V` with equal SHA-256 per shared path is required (§5.4).
4. Content hashes detect substitution (§5.3); any missing, copied, substituted, or unclassified M1 input fails (§5.4).
5. The fixture-only M1 source-file allowlist is explicitly empty; `RecoveryTestSupport.cs` and acceptance tests are allowlisted only for `D6_4.Tests` (§5.4).
6. Generated inputs are fully recorded (generating target, normalized path, hash), never silently excluded, with only identified assembly-identity metadata differences allowlisted (§5.5).
7. Conditional-compilation control: the effective `DefineConstants` sets are compared (variant may add exactly the fixture symbol); all inputs are scanned for the symbol; only the friend block and the fixed marker/Reconciler declarations may be guarded; both configurations are parsed with their actual preprocessor symbols and normalized active source outside the allowlisted regions is compared (§5.6).
8. The variant therefore provably consumes the real production `Reconciler.cs` (set membership + identical hash).
9. No copied or parallel production tree is permitted (§3; amended D6.4 §4).
10. The verifier fails on drift in either direction, unexpected generation differences, new symbol uses, or active-source differences outside the named regions (§5 closing).

Path identity, source-content identity, and compiled-code equivalence are correctly distinguished: the checks establish path+content identity and bounded conditional divergence; the documents do **not** claim compiled-control-flow identity and bound the acceptance claim accordingly (section 10). These checks are falsifiable and would catch an accidental divergence rather than restating an intention.

## 12. Blocking findings and optional observations

**Blocking finding (one):**

- **D6.5-R2a — The fixture-symbol DefineConstants delivery mechanism is unspecified, and the natural mechanism is demonstrably infeasible.** Affected sections: D6.5 §3 ("appends only `GAGAMBA_WP05_D6_4_TEST_FIXTURE` to the production DefineConstants set"; variant table row "Production set plus only GAGAMBA_WP05_D6_4_TEST_FIXTURE") and the amended D6.4 §4 variant-property paragraph. Source/evaluation basis: (a) independent evaluation shows a global `DefineConstants` carrying only the symbol evaluates as the symbol alone, discarding the SDK's `TRACE;RELEASE` (project assignments cannot override global properties); (b) `Microsoft.NET.Sdk.BeforeCommon.targets:290-298` appends the implicit framework constants by target-execution-time assignment, which a global `DefineConstants` also suppresses, so the naive route drops the entire SDK constant set, not just two constants; (c) MSBuild splits `Properties`/`-p:` values on `;` (observed `MSB1006`), so a multi-constant union requires `%3B` escaping. Practical consequence: an implementer following the document as written produces a variant that fails the design's own §5.6 set-equality verifier, or is tempted to weaken the invariant. Smallest required correction: in D6.5 §3 (and the D6.4 variant-property paragraph), name a working delivery mechanism — for example, pass a dedicated custom global property (e.g., `GagambaD64FixtureDefineConstants=GAGAMBA_WP05_D6_4_TEST_FIXTURE`) on the `D6_4.Tests`→M1 reference and append it to `DefineConstants` inside the M1 project via a conditioned assignment or a target running before `CoreCompile`, never by passing `DefineConstants` itself as a global property; state that the §3 edge-removal list must track the actual variant global properties (adding the carrier property; `DefineConstants` removal remains as defense in depth). This is a documentation amendment within D6.5's scope; no redesign of the fixture or the same-project mechanism is required.

**Optional observations (non-blocking):**

1. Runtime nuance: name-based friend matching also applies at runtime when a matching-named assembly is actually loaded; the documents' "compile-time access" phrasing is consistent with their "not a runtime sandbox" statement but could say this explicitly.
2. `BaseIntermediateOutputPath`/`BaseOutputPath` values must end with a trailing slash for correct MSBuild path concatenation; worth one sentence in §3.
3. §6.7's disjointness holds for the M1 project instances and `D6_4.Tests`; `Gagamba.Execution` artifacts are intentionally shared by both graphs (same identity by design), so concurrent production and variant builds could contend on the shared core's intermediates — standard shared-dependency serialization caveat, worth a note.
4. The static `-getItem`/`-getProperty` evaluations do not exercise restore/NuGet asset generation for the variant paths; the future binlog and purity checks cover this — no action needed beyond the documented checks.
5. Naming the exact reference metadata attribute (`GlobalPropertiesToRemove`, honored as MSBuild task `RemoveProperties`, `Microsoft.Common.CurrentVersion.targets:1044-1102`) would make §3 fully implementable without interpretation.
