## 2. Terra's original finding (D6.3 review, section 6)

Terra accepted the D6.3 `NotAttempted` outcome expectations for R1-T13–T15 but found the rows did not specify how a test supplies `KillDispatchOutcome.NotAttempted` or injects each fallback observation. The documented R12 bounded stop always calls `WriteKill` before its population read (`DomainLease.cs:108-143`), so setting only `FakeDomainBackend` population state cannot produce the typed stop outcome. Terra's smallest required correction: amend R1-T13–T15 to name the test-only typed-outcome seam that supplies `Kill=NotAttempted` without calling `WriteKill`, state that `ReadPopulation` is injected as Empty, Populated, and Unknown/inconclusive respectively, and retain the existing component, aggregate, durable-evidence, and no-successful-dispatch assertions. D6.4 is the response to exactly that finding.

## 4. Test-build assembly isolation verdict

**Mechanism sound; metadata wiring as documented is incomplete and one stated invariant is currently unreachable without an unstated source edit.**

Verified against the actual build configuration:

- `Directory.Build.props` defines no `DefineConstants`; no M1 source contains any existing `#if`. `GAGAMBA_WP05_D6_4_TEST_FIXTURE` therefore cannot leak into any other project, and the production build (symbol undefined) excludes every guarded type, field, overload, and branch. The conditional boundary is precise, and the normal production M1 assembly can be built with no fixture type, overload, or synthetic branch (questions A1–A3: yes).
- The variant has an unambiguous assembly identity (`Gagamba.Execution.Linux.M1.TestFixture`) with isolated `obj`/`bin` and `IsPackable=false`; M1 itself is already `IsPackable=false` in `src/Gagamba.Execution.Linux.M1/Gagamba.Execution.Linux.M1.csproj` (question A4: yes).
- Owner (`src/Gagamba.Execution.Linux.M1.Owner/Gagamba.Execution.Linux.M1.Owner.csproj`) references M1 by explicit project path and resolves the referenced project's `AssemblyName`. A distinct variant assembly name makes accidental binding impossible without an Owner csproj edit, and the proposed future build check ("production M1 contains no marker type or overload; Owner resolves the regular M1 assembly") is a meaningful artifact-level assertion, not a filename comparison (questions A5, A7, A8: yes, with the source-graph extension required below). M1.Tests builds Owner only via `ReferenceOutputAssembly="false"`; the D6_4.Tests project's declared "does not reference/build Owner" is consistent and stricter.
- `InternalsVisibleTo` routes (question A6): **as currently written, no.** The existing M1 friend grants are assembly-scope attributes inside shared source — `Execution/TransactionStateModel.cs:11-12` grants `Gagamba.Execution.Linux.M1.Tests` and `Gagamba.Execution.Linux.M1.Owner`, unconditionally. "Compile the M1 sources as a separate assembly" compiles those attributes into the variant too, so the variant would carry `InternalsVisibleTo("Gagamba.Execution.Linux.M1.Owner")` and `InternalsVisibleTo("Gagamba.Execution.Linux.M1.Tests")`, directly contradicting D6.4's stated invariant that "the M1 test-variant assembly metadata grants internals only to `Gagamba.Execution.Linux.M1.D6_4.Tests` and omits `InternalsVisibleTo("Gagamba.Execution.Linux.M1.Owner")`". Under the documented mechanism alone, that invariant cannot be reached; Owner-friend access to the variant's internal marker would remain a (latent, unreferenced) route. Additionally, the proposed `D6_4.Tests` assembly compiles the linked `RecoveryTestSupport.cs`, which consumes `Gagamba.Execution` internal types (`using Gagamba.Execution.Restricted`; `OwnershipSnapshot`, `IJournalStorage`, codecs), so `Gagamba.Execution` must also grant a friend to `Gagamba.Execution.Linux.M1.D6_4.Tests` — analogous to the existing `RestrictedManifest.cs:12` grant to `Gagamba.Execution.Linux.M1.Tests`. D6.4 names only the `Gagamba.Execution.Linux.M1.TestFixture` grant and misses this one; as specified, the D6_4.Tests project would not compile.
- Wording defect: calling the `RestrictedManifest.cs` addition a "compile-time-only friend declaration" is imprecise. `Gagamba.Execution` is built once and shared, so the attribute is emitted unconditionally into the production `Gagamba.Execution` assembly's metadata. It adds no runtime method or public surface (as D6.4 correctly states), and the marginal exposure is one more friend *name*, consistent with the existing `Gagamba.Execution.Linux.M1.Tests` precedent — but "compile-time-only" should not be read as absent from production metadata.

Required correction R1 (see section 9) resolves this cluster.

## 5. Production/test semantic equivalence verdict

**Conceptually correct and explicitly scoped, but the equivalence basis is asserted, not required.**

What D6.4 gets right:

- The fixture supplies only the typed stop result at the single stop-result boundary. Classification of that input (`NotAttempted` → `DomainStop=Unknown`), the fallback `ObservePopulation()` read, the `DomainEmpty` classification, aggregate precedence, journal finalization, and durable-progress persistence all execute in the shared `Reconciler` code. The document explicitly states the "ordinary planner, identity verification, live lease, fallback observation, aggregate, and journal paths remain active" and that the marker "changes only the stop result for the three defensive cases." Nothing in the proposal duplicates fallback logic, aggregate classification, or durable-progress logic in the fixture, and the marker cannot express success. This is not a prepared-`ReconcileResult` stub.
- In the production build (symbol undefined), the Reconciler's substantive control flow is unchanged; the divergence is confined to the variant's stop-result source. Differences between variants are attributable to the fixture boundary by construction of the guard.
- The C3 document amendment states the specification "targets a future isolated test-build variant, not the production assembly," which acknowledges the variant is not the production artifact.

What is missing: D6.4 never requires that the variant be compiled from the identical production M1 source set. "Compile the M1 sources as a separate assembly" implies it, but nothing pins the wiring (a variant csproj that links the production csproj's `Compile` items, or the same csproj with overridden `AssemblyName`/`DefineConstants` and isolated outputs), and the proposed future build check verifies only production purity (no marker in production M1; Owner resolves regular M1) — not variant source-graph identity. If a future implementation copies sources into a parallel tree, the fixture could silently diverge from production while still passing every proposed check, and the acceptance claim ("tests exercise the real classification and durable-progress logic") would rest on drift. Likewise, the limitation is acknowledged only implicitly; the equivalence argument (identical sources; divergence limited to `#if`-guarded members; production purity check) should be stated as the claim's basis, including the explicit acknowledgment that a test-built variant is not binary-identical evidence for the production assembly. Required correction R2 (section 9).

With R1 and R2 applied, the equivalence verdict is: sufficient. The evidence remains valid for the stated acceptance claim (future typed-classifier semantics), provided the variant provably consumes the production source graph. No smaller different seam is needed and no redesign is warranted; the mechanism is not structurally unsound.

## 6. Injection boundary verdict

**Correct, single, and post-checks; verified against the actual control flow.**

- Planning first: `Reconciler.Reconcile` calls `RecoveryPlanner.Plan` (`Reconciler.cs:149`); `Plan` (`:75-97`) requires matching boot, a live `AuthorityAlive` lease, and identity corroboration before `KillAndClean`. All three fixtures keep a live, matching lease (T15 sets only `ReadFault`; it does not dispose or mismatch the lease).
- Identity verification runs at the boundary preconditions: with the `DomainStop` bit clear (seeded `CompletedCleanup=0x08`), execution reaches `liveLease!.VerifyIdentity()` (`:224-228`) before any stop input is consulted; a mismatch returns `Refused` before the boundary.
- The synthetic result enters after those checks and only while `DomainStop` progress is unconfirmed (`:217` gate) — exactly the documented scope.
- `StopAndAwaitEmpty()` — and therefore `WriteKill()` (`DomainLease.cs:116`) — is bypassed only in the fixture path. `RequestStop()` (`DomainLease.cs:98-100`), the only other `WriteKill` caller, is not invoked anywhere in `Reconcile`. `WriteKillCalls=0` is therefore source-grounded, and no successful kill or termination is inferred anywhere in the flow (`NotAttempted` yields `DomainStop=Unknown`, never `Confirmed`).
- `ObservePopulation()` remains the real production method: with `DomainStop=Unknown` (future classifier), the `DomainEmpty` block reaches the retained fallback `liveLease.ObservePopulation()` (`:265`), which is a single non-looping call reaching `FakeDomainBackend.ReadPopulation()`. `ReadPopulationCalls=1` is thus both expected and measurable (Terra's requirement), and `StopPopulationObservation.NotObserved` truthfully records that the synthetic stop path did no polling.
- The fixture cannot skip meaningful classification or durable-progress logic: `DomainStop=Unknown` from the typed input, the `DomainEmpty` classification of the fallback result, the `TryPersist` mutations, the staging/removal component evaluation, finalization, and the aggregation at `:423-471` all run in shared code.
- No production caller can select the synthetic path: neither the marker type, the fixture field, nor the overload exists in the production build; Owner is outside the variant's graph. This holds provided required correction R1 closes the friend-metadata gap; as written, the variant's friend set is the one leak vector, and it is latent (Owner does not reference the variant) rather than a live path.

## 8. Durable progress and side-effect assessment

- R1-T13: only `DomainEmpty` is newly confirmed — `bits` go from seeded `0x08` to `0x0A`; `DomainStop` (`0x01`) remains clear; `DomainStop=Unknown` is never fabricated into `Confirmed`. Persistence uses the existing v3 record via `TryPersist`/`WriteMutation`; no new record kind, field, or schema. Healthy writer → `JournalFinalization=Confirmed` (`:460-464`). Aggregate `QuarantinedUnknown`. The final durable `Cleanup` state becomes `OwnershipCleanupState.Unknown` via the final `TryPersist(bits, verdict)` (`:460`); D6.4's prose "cleanup remains Unknown" is accurate for the final state, though the seeded value is `InProgress` — a wording nicety only.
- R1-T14/R1-T15: neither domain bit is newly confirmed; durable `CompletedCleanup` stays `0x08`; only the final `Cleanup=Unknown` transition persists. Aggregate `QuarantinedUnknown`.
- Negative assertions, all source-grounded: `WriteKillCalls=0` (only `StopAndAwaitEmpty` and the uncalled `RequestStop` dispatch kills); no fabricated dispatch (`NotAttempted` is never `Accepted`); no `CleanupConfirmed` (any `Unknown` required component forces `QuarantinedUnknown`, `:437-442`; `verdict=Unknown`); no deadline reset (the fixture path never touches `_clock`; `FakeDomainClock.Delays=0` and clock value unchanged are measurable); no new durable record/field; no unauthorized cleanup (staging cleaner never invoked with zero allocations; removal path skipped via the seeded bit); classification uses typed fields and `Known`/`Empty` booleans only — no diagnostic error-string parsing anywhere in the flow.
- `DestructiveActionTaken`: D6.4's characterization is exact — `destructive = true` is set at `Reconciler.cs:230`, before the bounded-stop call at `:231`, so the flag is a path marker, not a syscall counter; redirecting the side-effect oracle to the backend operation counters is correct and avoids redefining the flag.

**Zero-removal-call challenge (explicit):** D6.4's claim is source-grounded and does **not** rely on any assumption that `DomainStop=Unknown` suppresses removal. The `DomainRemoval` block (`Reconciler.cs:389-421`) is reached regardless of the stop outcome; if the seeded `DomainRemoval` bit were absent, the fixture path *would* set `destructive = true` and call `liveLease!.RemoveIfIdentityMatches()` (`:398-399`), which dispatches `_backend.RemoveChild` after an identity re-check (`DomainLease.cs:176-196`). D6.4 correctly attributes the zero-removal guarantee to the seeded pre-existing bit — "This pre-existing removal bit avoids calling `RemoveIfIdentityMatches`; it is not set by the fixture or test run" — and the proposed `RemoveChildCalls` counter on `FakeDomainBackend.RemoveChild` makes the claim measurable rather than assumed. The claim survives the challenge unchanged; no correction needed here.
