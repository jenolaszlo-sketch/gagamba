## G. Ordered experiment backlog

Each probe records exact source, helper binary/hash/version, OS/build/kernel/libc/architecture, user/token context, prerequisites, raw bounded observations, positive/negative controls and cleanup. “Unsupported” and “not run” are results, never passing restrictions. A failed mechanism may eliminate one platform path without weakening the common profile.

Shared safety envelope S: unique execution nonce; synthetic data only; finite target lifetime (normally <=30 seconds), small child/allocation/file counts, maximum bounded output; independent host observer/watchdog outside the candidate boundary; an outer test-owned Job/cgroup/VM for emergency cleanup. No real secret stores, cloud metadata, credential agents, scheduled jobs or production services are touched. No process flood, host OOM or filling the host volume. Root/administrator provisioning is confined to disposable test resources and recorded. Outer restrictions must permit each positive control; outer denial cannot count as candidate enforcement.

Shared cleanup C: retain object identities and independent finite-survivor records before release. After every outcome, stop the entire outer fixture if necessary, reap test processes, close server endpoints, verify lifetime locks/domain emptiness, remove only owned mounts/cgroups/profiles/workspaces by object-safe traversal, and record residual objects separately. Do not recursively delete a target-supplied path. A cleanup failure leaves the probe failed/unresolved and blocks further reuse. Recovery tests deliberately retain only the named protected evidence/journal under the independent observer.

### P01 — Windows least-privileged token, files and broker access

- **Class:** Blocking architecture decision. **Findings:** AR7-F02/F05/F09.
- **Question:** Can a non-admin caller create a supported, inspectable LPAC execution with a useful native closure and no ambient protected-resource or broker authority?
- **Mechanism:** Pin SDK declarations and supported OS API contract; unique identity; no application/network capabilities; protected RO executable/input copies; scratch-only writes; Job ownership. Compare ordinary user, ordinary AppContainer and candidate LPAC against synthetic files/registry/pipe/COM endpoints with user, Everyone, AAP and ARAP permissions. Inspect token/privileges/integrity from outside. Test a finite synthetic broker capable only of launching its fixture child outside the candidate Job. Where safe, test access/activation refusal to real WMI/SCM/task interfaces without issuing durable commands.
- **Expected outcomes:** Unrestricted positive control works; the candidate reads allowed copies, denies protected sentinels and cannot request out-of-domain work. Broad ambient readability, usable host-authority IPC or an undocumented-only creation path means the native architecture remains blocked. An unavailable broker endpoint gives no denial evidence for that endpoint.
- **Safety:** S; no modifications to existing system/home ACLs, real tasks/services or global firewall settings. A real broker execution experiment, if later necessary, belongs only in a disposable VM with a finite child and independent cleanup.
- **Cleanup:** C plus delete unique test identity/profile and compare registry/profile residue inventory.
- **Decision:** Select supported LPAC path only if its effective baseline is bounded; otherwise evaluate extra restriction mechanism or VM. Do not add blanket compatibility capabilities.

### P02 — Linux same-UID control-plane denial

- **Class:** Blocking architecture decision. **Findings:** AR7-F03/F05/F07.
- **Question:** Does the rootless namespace/helper composition deny all target access to the manager's controller resources despite mapping to its host UID?
- **Mechanism:** Native non-root UID with a unique delegated parent and memory/pids controllers. Pinned non-setuid Bubblewrap candidate, private user/mount/PID/network/IPC namespaces, closed setup FDs, capabilities dropped, `no_new_privs`, explicit seccomp. Keep parent/sibling controls manager-writable as the positive control. Target attempts self/descendant migration, subtree creation, controller/limit modification, proc-root/FD recovery, cgroupfs mount, `setns`/`unshare`, clone namespace flags, ptrace/process-memory/pidfd attacks and synthetic daemon-socket access.
- **Expected outcomes:** Manager successfully moves a finite control child within its fixture parent; restricted target cannot mutate or reach controls and remains in its owned group. If access succeeds, evaluate Landlock or separate host UID before selecting architecture. No conclusion from root-only runs or read-only outer cgroup mounts.
- **Safety:** S; run a migration-positive child only between siblings of the outer test parent. No writes outside that subtree, no host namespace changes.
- **Cleanup:** C; outer `cgroup.kill`, `populated 0`, child/sibling removal, namespace/mount/FD inventory and reaping. Verify manager control remains usable after denied attacks.
- **Decision:** Accept rootless separation as candidate only with actual denial evidence; identify required distro/LSM/userns/controller prerequisites. If prerequisites are unacceptable, bring broker/VM decision back.

### P03 — Offline transports and host IPC

- **Class:** Blocking architecture decision. **Findings:** AR7-F02/F05.
- **Question:** Does each candidate deny communications beyond prepared pipes, including indirect broker/network paths?
- **Mechanism:** Synthetic IPv4/6 TCP/UDP listeners on loopback and controlled LAN; test DNS server and proxy; simulated metadata endpoint in an isolated test network (never real cloud metadata); Unix pathname/abstract sockets or named pipes and one finite broker. Check inherited connected socket/handle rejection. Linux includes private loopback, socketpair, raw/netlink families, alternate syscall ABI and `io_uring` attempts. Windows includes network capabilities/exemptions, private inbound listeners and app-container object naming. Test direct OS APIs, not only an HTTP client honoring environment settings.
- **Expected outcomes:** Positive unsandboxed controls reach all tested endpoints; same executable under profile reaches none, including intra-execution IP loopback. Allowed anonymous pipes work. If internet connectivity cannot be provisioned, record that leg pending; local denial does not by itself qualify the real internet leg. A missing DNS/proxy/IPC endpoint is not a pass.
- **Safety:** S; endpoints under test-owner control, nonce payloads only, no scans or contact with real agents/brokers. No broad firewall changes to manufacture a result.
- **Cleanup:** C plus independent endpoint receipt counters, listener shutdown and removal of test socket/pipe objects; no leaked established connections.
- **Decision:** Require a stronger composition or refuse if any ungranted transport works. Distinguish no-network from no-host-IPC in the final effective manifest.

### P04 — Resource and complete writable-storage viability

- **Class:** Blocking architecture decision. **Findings:** AR7-F06/F09.
- **Question:** Can the required ceilings be established with useful runtime compatibility and without a new privileged service?
- **Mechanism:** Windows Job process/commit limits and candidate finite store; enumerate AppContainer profile/registry and every other writable location. Linux delegated memory/pids controllers, swap policy, finite tmpfs byte/inode bounds, private `/dev/shm`, descriptor limits. Measure native charging categories and trusted-helper overhead. Small child/thread/memory/file/handle stress, create/delete loops, sparse files, mapped writes, metadata and output spill attempts. Verify limits cannot be raised by target. Compare a native fixture, NativeAOT and a self-contained .NET closure.
- **Expected outcomes:** A below-budget workload runs; bounded above-budget operations fail/stop with a trusted observation, and host fixture reserve remains intact. Linux N-task limit must be reported as such; increasing tasks must not be called an N-process cap. Windows profile/registry storage escaping the finite store fails. A 128 MiB .NET startup failure is incompatibility, not permission to increase the budget.
- **Safety:** S; outer hard limits and pre-reserved small storage; incremental allocations with fixed maxima, never testing by exhausting host resources. Separate outer-only limits from actual candidate limits using readback and tighter inner controls.
- **Cleanup:** C plus memory/process counters return to baseline, volume/tmpfs/profiles unmounted/removed, no persistent log/core-dump spill. Preserve storage residue if deletion is uncertain.
- **Decision:** Approve native resource semantics only if useful and honest; decide conservative task ceiling vs revised contract openly. Windows may need provisioned storage/VM or remain unsupported. CPU/handle/thread residual DoS may veto workstation suitability.

### P05 — Immutable preparation and release protocol

- **Class:** Required before implementation. **Findings:** AR7-F01/F04/F09/F10.
- **Question:** What is the smallest preparation/release seam that binds authorized authority without changing the frozen lifecycle contract unnecessarily?
- **Mechanism:** Disposable harness, no public API change. Normalize intent; stage fixed synthetic closure; bind objects/digests; issue single-use preparation; establish all restrictions; final deadline/cancel check; release through a trusted control channel not inherited by target. Vary caller collection values and replace input/executable/cwd/runtime/manifest paths at barriers. Swap preparations between providers, replay them, and delay setup beyond budget. A trusted harness controls these replacements; no concurrent mutation of real user trees.
- **Expected outcomes:** Exact authorized snapshot runs once; altered authority, stale objects, wrong issuer, expired deadline or stop-won release never yields target nonce. Unsupported profile cannot invoke ordinary lifecycle launch. Failure after trusted helper starts distinguishes “helper ran” from “target ran.”
- **Safety:** S; tiny fixture binaries and fixed test paths.
- **Cleanup:** C; reclaim partial preparation, retained handles, private staging and issued-token state on each injected failure.
- **Decision:** Approve only the minimal additive seam justified by these cases. Never equate AR-4 value snapshot with executable identity binding.

### P06 — Filesystem closure and export escape proof

- **Class:** Required before implementation. **Findings:** AR7-F04/F09.
- **Question:** Can preparation, runtime writes and post-stop exports preserve authority under hostile object classes and replacement?
- **Mechanism:** Controlled files, sibling prefix names, absolute/relative paths, symlink/junction cycles, hardlinks, mount/reparse aliases, case/short-name/ADS variants, path exchanges, executable/library replacement, RO/RW object aliases, synthetic credential trees. Use object handles/FD-relative resolution; Linux `openat2` resolution constraints are a candidate, not a complete snapshot mechanism. Copy regular inputs into new objects; verify final binds. Race output replacement before stop and export.
- **Expected outcomes:** Allowed file read/write/export works; no denied sentinel is readable or modified; unsupported inputs fail before release; protected closure cannot be altered after preparation. Export rejects links/special objects and never overwrites arbitrary caller paths. Host source changes after copying do not change staged execution.
- **Safety:** S; all links/mounts point only to controlled sentinel trees. Do not probe actual credential files.
- **Cleanup:** C with no-follow, identity-bound deletion; attack-created paths never enlarge cleanup scope.
- **Decision:** Select protected copies plus handle-bound access, or reject unsupported filesystems/classes. No broad grant workaround.

### P07 — Crash, root status, owner death and release races

- **Class:** Blocking architecture decision. **Findings:** AR7-F07/F10.
- **Question:** Does the actual setup topology preserve target ownership, root result and bounded stop through every crash transition?
- **Mechanism:** Barrier-controlled finite tool/child. Windows crash before create, after create/before assign, after assignment/before release, after release; compare job-at-create and current suspend/assign path. Linux crash caller, Gagamba manager, helper/guardian and namespace init independently; test parent-death arming races, blocked/drained pipes, root exit while children live, attempts to duplicate lifecycle handles and attack guardian. Independently verify target root exit differs from wrapper/init exit. Arm deadline before release.
- **Expected outcomes:** No unowned target is released; released work stays restricted and stops within the stated healthy-host bound on owner failure. No target can keep a control handle/channel alive to defeat death detection. One execution-owned terminal result persists across observer cancellation. Unknown status remains Unknown; stale/recycled identity never causes unrelated process termination.
- **Safety:** S; only fixture processes are killed; finite self-expiry and outer ownership even for deliberate leaks.
- **Cleanup:** C; independent witness confirms every descendant dead, cgroup/Job empty, root reaped; record residues separately from process stop.
- **Decision:** Choose helper topology/atomic ownership only after this evidence. If an existing helper cannot support truthful root/terminal semantics without substantial patching, revisit helper vs bespoke launcher. A watchdog claim must remain Constructed.

### P08 — Runtime baseline and complete consumer usability

- **Class:** Required before qualification. **Findings:** AR7-F04/F06/F09.
- **Question:** Can one useful tool run from a reviewable closure at declared budgets without widening host authority?
- **Mechanism:** Native fixture then one self-contained .NET tool; optional explicitly staged interpreter or Git only after these. Pin runtime/packages, enumerate native libs/configs/baseline resources; run from prepared input to scratch and bounded export. Disable unnecessary diagnostics/startup hooks; repeat with poisoned HOME/PATH/proxy/loader/agent variables. Test custom Windows argv parser limits explicitly if relevant.
- **Expected outcomes:** Useful result with exact effective manifest; unsupported dependency/IPC request fails clearly. .NET JIT, threads, GC, globalization and temp needs are measured, not assumed. Offline build/test is not promised merely because a small .NET program runs.
- **Safety:** S; no package restore/network/install during target run; synthetic projects without real source secrets.
- **Cleanup:** C and export integrity checks; no runtime caches or diagnostic sockets outside owned storage.
- **Decision:** Admit only the demonstrated runtime baseline; document user-visible preflight errors. Larger tool families require new closures/qualification, not broad host mounts.

### P09 — Security manifest and installed-package gate

- **Class:** Required before qualification. **Findings:** AR7-F01/F10.
- **Question:** Can stale, incomplete, tampered or self-reported security evidence be rejected independently of lifecycle evidence?
- **Mechanism:** Extend a separate future AR-7 gate, retaining AR-6 lifecycle checks. Bind exact source/packages/helper/filter/closure/profile/test digests and native host prerequisites. Negative controls: changed SHA, helper version, filter byte, rootless privilege context, omitted denial leg, skipped mandatory test, false positive endpoint, target-written receipt, unknown cleanup, package consumer using wrong provider or legacy fallback.
- **Expected outcomes:** Only complete native profile evidence and same-package consumer pass. macOS refusal is tested as refusal, not as enforcement coverage. Changed security-sensitive dependencies invalidate prior candidate seal.
- **Safety:** S; mutate copies of synthetic/AR-7 evidence only. **Do not alter the retained AR-6 manifest or seal.**
- **Cleanup:** C for installed consumers; evidence fixtures stay in their own bounded artifact directory.
- **Decision:** Keep AR-7 held until the independent gate is negatively tested; reports must retain missing/skipped counts.

### P10 — Reopen macOS only with a supported deployment choice

- **Class:** Nice to know while macOS is refused; **Blocking architecture decision** if macOS support is required for v1. **Findings:** AR7-F08.
- **Question:** Can a publicly supported signed App Sandbox helper product, or a VM worker, meet the same complete profile?
- **Mechanism:** Native SDK/header/support review distinguishes supported entitlements, legacy/deprecated sandbox APIs and private SPI. Small signed helper with child inheritance, static/dynamic grants, Mach/XPC endpoints, synthetic agent, filesystem and network denial. Independently test setsid/launchd-broker effects, process/resource ownership and bounded capture. Compare a VM only if its deployment and guest execution semantics are accepted.
- **Expected outcomes:** Document complete mechanism/support evidence or retain refusal. Inheritance success alone does not solve lifetime/resource gates. No claim that undocumented Seatbelt profiles are stable merely because they run today.
- **Safety:** S; native disposable macOS test user/VM, synthetic services, no real launch agents/credentials. No private entitlements in production.
- **Cleanup:** C plus signed helper/launchd labels/container data and escaped fixture descendant sweep under independent ownership.
- **Decision:** Return to architecture approval; do not treat macOS as a translation of Linux flags.

### P11 — Performance and optional improvements

- **Class:** Nice to know. **Findings:** AR7-F09.
- **Question:** Are closure reuse, CPU-rate bounds or extra Landlock rules worth their maintenance cost after the profile works?
- **Mechanism:** Repeated bounded cold/warm setup measurements; compare immutable cache keyed by closure digest with copies, CPU-limit controls and optional Landlock layering. Never share target-writable caches between runs. Include dependency invalidation.
- **Expected outcomes:** Measured cost and clear security/usability benefit; no changes to baseline grants or profile interpretation.
- **Safety/cleanup:** S/C; finite repetitions, recorded cached object ownership; no new permanent service.
- **Decision:** Defer absent evidence of need. Remote execution and a universal quota framework remain out of scope.

Denial needs trusted endpoint/object observations plus established mechanism evidence.

### Oracle and coverage rules

1. Every test leg uses a fresh nonce/workspace and proves that its positive-control prerequisite exists. If the positive control cannot perform the operation, the negative result is inconclusive. A helper crash is not a successful policy denial.
2. Observe effects outside the target: controlled server logs, unchanged sentinel hashes, native token/namespace/controller state, root status and OS-held lifetime locks. Record attempted operation acknowledgements through a bounded channel, but never accept target-written JSON as the security receipt.
3. Use the same candidate binaries/helper/filter for positive authorized behavior and restricted denial; separate unsandboxed controls live only in test tooling. A never-launching provider must fail the matrix, following AR-6's broken-provider doctrine.
4. Missing/skipped mandatory profile cases block that platform. “Not applicable” requires a named semantic equivalent or a true OS-specific surface absence, reviewed explicitly. An inaccessible real service is not proof that reachable services would deny the target; use a controlled reachable surrogate and verify the actual OS token/IPC restrictions.
5. Root WSL validates only its stated context. Native non-root Linux with genuine controller delegation must pass separately. Windows ordinary user, supported OS builds and nested-host-Job scenarios must be explicit. macOS refusal needs native proof of no target release; it earns no restricted-enforcement claim.
6. Re-run relevant lifecycle regressions after integration. Reuse the lifecycle contract and evidence format; do not reuse an earlier passing SHA as qualification for changed native source, helper, seccomp filter, runtime baseline or package bytes.

### Security qualification manifest proposal

The future machine-readable manifest should bind: schema version; exact Git SHA and clean-tree status; package IDs/versions/hashes; native helper and dependency hashes; profile/revision/digest; filter and runtime-baseline digests; host OS/build/kernel/libc/architecture; user/token and delegation context; mandatory mechanism readback; native test leg identities/results/positive controls; installed-consumer results; cleanup components and residuals; explicit unsupported platforms/features; trusted collector identity and artifact hashes. Any signature or seal attests this record's provenance, not mathematical completeness of its tests.

Keep native evidence and public receipts separate: the former may contain protected diagnostic object identities; the latter defaults to redacted invocation/environment/output. No secrets, live handles or reusable authority tokens belong in either artifact. Store the new security manifest alongside the future AR-7 evidence, never inside the frozen AR-6 candidate archive.
