# Authenticated context, cross-format handoff and P4

Symbols describe responsibilities. The proposed types and files are subject to separate entry authorization.

| Boundary | Independently established input | Result, ownership and refusal |
|---|---|---|
| Future original-parent INIT and local ACK | Authenticated original parent and child association, held actor identities, received credential and descriptor evidence, original private capability/catalog and loaded-role checks, original session/execution/lease, phase, expected direction and sequence. | Compare header, digest fields and actual supplied provenance evidence against the original association. Compare ACK capability digest against retained context after local checks. Own immutable session-scoped context. Missing provenance or context, substitute pins, digest/ID disagreement, wrong role/phase/length and replay refuse. |
| Future E-3 bootstrap call | Already authenticated INIT under the original association, separately verified matching pre catalog, selected topology/context, original capability SHA-256 and independently supplied original E-3 projections and digests. | The unchanged E-3 R2 structural codec returns bounded v3-pre data on success. Compare the independently supplied digest to decoded `AuthorityHash` and preserve explicit original identities by value. Keep v3-pre structurally distinct from Qualified. A parse or equality result supplies no actor, catalog or authority provenance. |
| Future direct context | Original C/O pins from accepted S3, verified original direct-peer and same session tuple, retained independently authenticated inherited context and both hashes. | C type 6 and O type 7 confirm that same context with original peers. Never promote an inherited ACK into direct proof. An incomplete, timed-out, replayed or mismatched exchange cannot unlock Ready or staging. Keep the original deadline and stop service. |
| Cross-format integrity and release | Preserve original capability, catalog, script and action hashes, LE action index 2, original session/execution/lease/preparation .NET GUID bytes in order and local preparation manifest digest. Installation/verification digests and release digest retain distinct purposes. | E-4 accounts for exact identity preservation. Existing `ReleaseRequest.ApprovalCorrelationSha256` carries the existing 32-byte value specified by the adopted 258-byte preimage. E-4's proposed managed scope does not create release messages, compute for runtime use, set `HasApproval` or enforce release. E-6 owns recomputation from the owner's independently verified immutable preparation context and the atomic pre-write gate. |

Use retained immutable comparison data for structural tests and avoid aliasing mutable buffers. Synthetic contexts represent test operands and do not manufacture an authenticated context. Real descriptor lifetime, acquisition, disposal of delivered rights, independent stop/reap, held-original proof and custody remain later responsibilities. The E-2 accepted structural verification outputs are available as design references. Protected reads and genuine V/W/A, R/Wc/P, live issuance, approved case policy and activation remain independently gated.

## P4 evidence and gates

P4 is refusal-only. Source review compared the frozen E-3 P4 inventory with the current revision and examined the existing installed admission, direct context and preparation entry points. The published revision introduced no code beyond previously accepted R2. The proposal leaves the only installed S10/S11 route dominated by upstream admission, S28 test-only, and existing authority/effect ordering under accepted P4. An actual E-4 candidate requires an exact-revision source delta and caller/sink/authority re-audit. Require both Debug and Release metadata scans of M1, Owner, Recovery, InstallTool and actual copies, positive known-test callers, and zero production callers or trusted conversions. Run the production verifier on Release and on Debug as a negative control, the production-build policy controls and the preparation validator. Observation-to-effect residual and O-R3 refusal-reason typing remain open. F-R1/O-R1 and O-R2 retain their future-caller triggers. A live first effect or first E-1 consumer also requires the distinct approvals and F-02 review and Option A reassessment at the responsible gate.
